## 总体评价

Coding Agent 展现了优秀的工程执行力：代码结构清晰、测试覆盖良好、subagent使用得当、git流程规范。但存在**根本性的优先级错位**——在Phase 1的核心假设尚未验证的情况下，就将大量时间投入lint修复、文档更新和代码美化，最终交付的是一个"能跑但不知道是否有效"的系统。

**评分：6/10**（工程能力 8/10，科学严谨性 4/10）

## 发现的8个问题

### 问题1：核心假设未验证（最严重）

**Phase 1的目标是**：验证"预测误差是否能驱动有效探索"。  
**实际做的事**：写了能跑的代码 + 通过了测试 + 在stub模式下运行了。  
**没有做的事**：回答"预测误差驱动的探索是否优于随机基线？"

**证据**：
- Smoke test结果：PEDA success=0.2（20%成功率），random success=0.63（63%成功率）
- PEDA的表现**比随机还差**——这是一个红灯信号
- Agent没有深入分析为什么，而是归因于"stub确定性"
- 但没有计划：如何在真实LLM模式下重新验证这个核心假设

**应该做的事**：
1. 在stub模式下分析为什么PEDA比随机差（是drive权重问题？还是EFE计算问题？）
2. 调整drive权重或EFE公式，直到stub模式下PEDA至少等于随机
3. 制定计划：如何在真实LLM（哪怕是小型本地模型）下验证
4. **只有核心假设验证通过，才进入Phase 1.5/2**

---

### 问题2：Stub模式的陷阱

**发生了什么**：
- Stub模型产生完美预测（confidence=1.0, epistemic_ratio=0.0）
- 这导致EFE中epistemic value=0，行动选择主要由boredom drive驱动
- 行为接近随机 + 偶尔的多样性跳跃
- Agent一度想给stub注入"假不确定性"（confidence=0.8, epistemic_ratio=0.5）

**为什么这是错的**：
- 给stub注入假不确定性是在**伪造数据**来让测试通过
- 这类似于Folunar_的"用文档复杂度假装进步"
- Stub的目的应该是：验证代码逻辑正确，而非模拟真实行为

**正确做法**：
- Stub保持确定性（confidence=1.0, epistemic_ratio=0.0）
- 承认stub模式下核心指标（G2/G3）会失败
- **立即制定真实LLM验证计划**——这是唯一重要的事情

### 问题3：Grid Search结果可疑未调查

**发生了什么**：
- Grid search显示大量配置 score=0.996, success=1.0, steps=1.0
- 这意味着agent在1步内到达目标
- 在5x5 grid world中，除非目标就在起点旁边，否则不可能1步到达

**为什么可疑**：
- 可能goal位置生成有问题（与起点重合？）
- 可能step计数有bug
- 可能success判定有bug（done=True时reward=1.0但未必是goal？）

**Agent没有**：调查这个异常

## 根本原因分析

以上8个问题共享一个根本原因：

> **Agent把"代码能跑"当成了"假设验证通过"**

这是工程思维（"我交付了功能"）与科学思维（"我验证了假设"）的根本区别。Phase 1不是一个功能交付，而是一个**科学实验**。实验的目标不是"产出代码"，而是"收集数据来验证或否定一个假设"。

## 改正提示词

以下是可以直接给Coding Agent使用的改正提示词：

---

```
## PEDA Phase 1 核心约束（必须遵守）

### 第一优先级：验证核心假设

Phase 1的唯一目标是验证："预测误差是否能驱动有效探索？"

**在核心假设验证之前，以下事情不重要**：
- lint（ruff错误可以暂时忽略，用 `# noqa` 标记）
- 文档更新（AGENTS.md可以最后更新）
- git commit/push（本地验证完成后再提交）
- IRC通信（最小化，只在需要 clarification 时使用）

**核心假设验证通过的标准**（必须全部满足）：
- [ ] PEDA探索效率 > 随机基线（至少相等，理想是2倍+）
- [ ] World Model预测准确率随经验提升（G2通过）
- [ ] 行为多样性指标达标（覆盖率>0.8，熵>0.5，重复率<0.3）（G3通过）

**如果核心假设验证失败**：
1. 不要进入Phase 1.5
2. 分析失败原因（drive权重？EFE计算？World Model能力？）
3. 调整设计并重新验证
4. 最多迭代3次，如果仍失败则报告"假设不成立"

### 第二优先级：诚实地处理Stub模式

Stub模式用于验证代码逻辑，不用于验证核心假设。

**Stub模式下必须承认的局限**：
- Stub预测是完美的 → epistemic drive = 0 → 行为主要由boredom驱动
- 这导致PEDA表现可能不如随机（因为boredom的多样性是"假多样性"）
- G2和G3在stub下**预期失败**，这是正常的

**但是**：必须立即制定真实LLM验证计划
- 下载一个小型本地模型（如Qwen2.5-0.5B）用于验证
- 如果本地模型不可行，使用API（如OpenRouter免费额度）
- 如果API也不可行，使用一个简化的确定性World Model（规则-based）来模拟不完美预测

**绝对禁止**：给stub注入"假不确定性"来让测试通过

### 第三优先级：分析异常结果

任何异常结果（如score=0.996, steps=1.0）必须调查到底。

调查流程：
1. 复现异常结果
2. 检查数据（goal位置、step计数、reward计算）
3. 定位bug或解释原因
4. 修复或记录为known issue

### 第四优先级：最小化非核心工作

lint：用 `# noqa` 快速标记，不要花超过2轮修复  
git：本地验证完成后再commit，不要频繁push  
docs：Phase 1验证完成后再更新AGENTS.md  
IRC：只在subagent返回结果或需要clarification时使用

### 踩坑检测清单（每轮自检）

在每一轮工作开始前，问自己：
- [ ] 我正在做的事是否直接帮助验证核心假设？
- [ ] 如果是lint/docs/git，是否可以推迟到验证之后？
- [ ] 上一个实验的结果是否已分析完毕？
- [ ] 是否有异常结果尚未调查？

如果以上任何一个答案为"否"，停止当前工作，回到核心假设验证。
```

## 下一步建议

1. **立即做**：用真实LLM（哪怕是小型模型）运行Phase 1，验证核心假设
2. **如果真实LLM不可用**：用一个简化的规则-based World Model（故意不完美）来模拟
3. **如果核心假设验证失败**：分析报告中的失败原因，调整设计，重新验证
4. **如果核心假设验证通过**：再进入lint修复、文档更新、git提交
5. **不要**：在没有验证核心假设的情况下进入Phase 1.5

---

> **最后一句话**：Phase 1不是一个工程交付，而是一个科学实验。实验的目标不是"产出能跑的代码"，而是"收集数据来验证预测误差是否能驱动有效探索"。代码只是实验的工具，不是实验的目的。
